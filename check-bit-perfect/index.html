Checking bit-perfect

How do I check if my player is bit-perfect?

Compare what reached the digital side of the chain with the file itself. That takes one of two things: a DAC with a built-in bit test, playing its maker's test file, or a capture of the digital stream compared with your file, sample for sample or by hash. Every other check can catch a player that changes your music. None of them can prove that one doesn't.

Bit-perfect means the DAC receives exactly the numbers that are in the file. Here are the checks people reach for, from weakest to strongest, with what each one can prove and what it can't. You don't need our app for any of them.

Listening

Listening tells you that two setups sound different to you. It can't tell you why. If two players deliver identical bits to the same DAC, the DAC has nothing different to convert, so a difference you hear isn't in the samples.

Level is the usual suspect. A bit-perfect path can't turn the volume down in software, because scaling a sample changes it, so the volume moves to the hardware. Google's documentation for Android's bit-perfect mode says so directly: "the hardware controls the volume as the framework doesn't provide any software volume control." Two players can send the same samples and leave the DAC's own volume in different places. A small level difference is enough to make two playbacks sound different, which is why a fair listening test matches levels first and hides which one is playing.

Recording the analog output

Recording the headphone or line output with an analog-to-digital converter is a real measurement. It shows level, frequency response, noise and distortion, and it will catch a player applying EQ or a volume change big enough to measure.

It can't prove bit-exactness. The DAC turns numbers into voltage and the recorder turns voltage back into numbers, each with its own noise and its own clock, so two recordings of the same file through an unchanged chain won't match sample for sample either. A small difference between two players' recordings doesn't prove their bits differed. A near-perfect match doesn't prove they were identical.

The DAC's rate display

Many USB DACs show the sample rate they're receiving, usually as a coloured light rather than a number. That's the DAC's own report from the far end of the cable, and it catches the commonest failure: a 44.1 kHz album arriving at 48 kHz because something converted it on the way.

It proves the rate and says nothing about the samples. Audio with its volume turned down in software arrives at the same rate as audio nobody touched, so the light reads the same for both. Which DACs report the rate, and how, is on which USB DACs show the rate they receive.

Android's own report

Android will tell you what its own audio output is doing. With adb connected, adb shell dumpsys media.audio_flinger lists each output with its sample rate, and the first line of each block names the kind of output. In Android's source code, an output running through the shared mixer is labelled MIXER, and on Android 14 or later an output opened in the platform's bit-perfect mode is labelled BIT_PERFECT. That report describes what Android's audio system is doing with the audio it was given. It can't see what the player did before handing the audio over, such as its own EQ or volume. And it sees nothing at all of a player that drives the USB DAC with its own driver, because that audio never goes through Android's mixer.

A DAC that runs a bit test

A few DACs check the bits themselves. RME's manual for its ADI-2 DAC describes one: play the short test file RME provides, and the display reports a pass along with the bit depth it detected. The manual lists what the test pattern catches: "Level changes, equalization, dynamic processing, polarity, channel swapping, sample offset, hanging or twisted bits, dither, bit reduction." It's plain about failure, too. If the path isn't bit-transparent, "the message is not shown" and "There is no error notice." So silence is a fail.

For checking any player, this is the most independent test on the list, because no code from the player has a say in the verdict. Its limit is the file. A pass proves the path was transparent for that test file, at that rate, with the volume and settings you had while it played.

A digital capture, compared with the file

A bit test settles it for a test file. A capture compared with the file settles it for your music.

Decode the file to raw samples on a computer, trim the capture so the two start on the same sample, and compare them: sample for sample, or by computing a SHA-256 hash of each and comparing the hashes. If they match, nothing changed a bit. Subtracting one from the other, a null test, leaves digital silence for the same reason. A tool such as ffmpeg decodes a FLAC to raw samples in one command, and our verification page writes the exact sample layout out.

The hard part is the capture. On a phone the USB stream is assembled inside the phone, and software can only watch it from the inside: our verification page calls the moment bytes leave for the DAC "a physical event only the code doing the shipping can observe." Outside the phone it takes hardware on the digital side of the chain, such as a recorder with a digital input fed from a digital output, and then the recorder has to be shown to pass its input through untouched as well. We haven't documented a setup like that, so this page doesn't give steps for one.

Why the check is worth repeating

A bit-perfect setting names a path. Whether your music stays on it depends on what happens while it plays. Google's requirement for Android's bit-perfect mode lists what would take it off: the stream "must not have any volume scaling, sample rate conversion, or audio processing effects and must not be mixed in the DSP." Turn the volume down in software, switch on EQ or ReplayGain, or play a file at a rate the DAC can't take, and the player has to do something about it even though the setting never changed. The checks worth having are the ones you can run again on the track that's playing.

Where Meringo fits

Meringo, the Android music player we build for USB DACs, does the capture from the inside. On its USB Direct path, arm Verified Capture in Settings, Audio diagnostics. Meringo writes every byte it hands to the isochronous pipe (the USB transfer that carries audio) and computes a SHA-256 over the whole stream. Point it back at the same file and it re-decodes it, lays the samples out in the identical format and hashes that. Matching hashes mean no resample, no requantise, no EQ and no ReplayGain touched a single bit between the file and the pipe. The verification page has the method and a public-domain checker script, a single file that needs Python 3 and your own ffmpeg and shares no code with Meringo, so you can recompute the hash from your own copy of the file.

Two limits, and we print both. The hash covers what Meringo put on the wire. Isochronous USB carries no delivery acknowledgement, so no software on any platform can prove what the DAC received, only what was put on the wire for it. And it checks Meringo only. It can tell you nothing about another app. We hold receipts for three DACs, the Fosi DS2, the Qudelix 5K and the Jcally JM6 Pro, and the registry takes every verdict, a mismatch included.
